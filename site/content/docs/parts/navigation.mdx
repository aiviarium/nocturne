This page shows how the navigation parts work together in an app.
Each part has its own page for its props.

## The shared sidebar

The app's sidebar is the `sidebar` of `AppShell`, usually a `Nav`.
Every view shares it, and it is usually there.
Pass `onSidebarResize` to make it resizable: its edge drags, and the arrow keys move it when it has focus.
The app keeps the width and passes it back as `sidebarWidth`.
The width runs from 180px to 420px.

Going deeper changes the main column, not the sidebar.
The sidebar keeps its width, its scroll and its current item while you drill down.

## The app's header

Most apps put the path in a header beside the sidebar, above the content, with the actions at its end.
`AppShell` has that bar.
A view fills it with a `ViewHeader` with `variant="shell"`.
The header is still part of its view, so the inspector toggle and the pin work as before.
The bar takes no room when no view fills it.

- The crumbs are at the start of the bar, at the left edge of the frame under it.
- `up` adds an arrow before the crumbs that goes to the level above, named after it.
  Give it to every level below the top, so going up is one click at the same place.
- The view's actions are at the end of the bar.
  The frame has no second header under it.

Use the view's own header in place of the app's when the shell shows more than one frame side by side, and each frame has its own path.

## Columns

A view has these columns, from left to right.

| Column | What goes in it | Width | When there is no room |
| --- | --- | --- | --- |
| Rail | An activity bar, the `rail` of `ViewLayout` | 36px | It stays |
| Shared sidebar | The app's places, from `AppShell` | 180px to 420px, the person resizes it | A drawer on a phone |
| View sidebar | The view's own navigation, such as saved views or a page tree | 180px to 420px, 240px at first | Hides and leaves the rail |
| Main column | What the view shows | At least `minMain`, 560px by default | It stays |
| Inspector | The properties of the selection, an outline | 200px to 360px, 260px at first | Collapses behind its toggle |
| Bottom panel | Output, logs, a terminal, in a vertical `Split` | Dragged by its divider | It stays |

`ViewLayout` lays out the view sidebar, the main column and the inspector.
Each side column resizes by its edge, and a click on the edge hides it.
Widths and collapsed columns are kept per view on the device.

- A side column collapses by itself when the main column would get narrower than `minMain`.
- Opened by hand, a column docks beside the main column while the main column keeps 360px.
- Below that, the column opens over the main column, with a scrim. Escape or a click on the scrim closes it.

Alt B toggles the view sidebar and Alt Shift B toggles the inspector.
Tab moves focus through the columns in order.
Escape in a column opened over the main column closes it and returns focus to its toggle.

## Bars

| Bar | What belongs in it |
| --- | --- |
| Top bar | On a phone, the control that opens the drawer. Nothing on a desktop |
| App header | The path to the open view with its up arrow, and the view's actions. A `ViewHeader` with `variant="shell"` fills it |
| `TabStrip` of a `Frame` | One tab for each open view, with the name of the view |
| `ViewHeader` | The crumbs or a back control, short context, and the actions of the view, when the app's header doesn't hold them |
| Status bar | Only what is out of the ordinary, such as a lost connection |

Each thing goes in one bar, and the other bars don't repeat it.
The name of the view is in its tab.
The header never repeats it as a heading.
The view's actions sit in its header, with no second toolbar under it.

## Drill down or nest

Drill down when the target is a domain of its own with enough nested data to fill a view.
Projects drill down to the issues of a project and then to one issue.
The fleet drills down to a host and then to its sessions, tasks, units, logs and processes.

Nest in place when the data is a part of one view.
Use the view sidebar for saved views, `Nav` groups for sections, and a tree for pages.
Choosing an item in place changes the main column and keeps the view.

To choose, ask whether the target has its own lists, its own inspector and its own actions.
If it does, drill down.
If it is one more level of the same list, nest it.

## Crumbs

The crumbs show the path to where you are.
The view picks one of three forms for each target.

- **Full path.** Each level as a crumb, as in `Atlas web / Issues`. Use it when the path is short, and in a tree, where the crumbs show where the page sits.
- **Stripped path.** Drop or fold the leading levels, so the levels that help you move stay. `fold={1}` turns the first crumb into `…`, a menu of the folded levels, as in `… / Atlas web / WEB-142`. To drop levels, pass only the crumbs you keep.
- **Back control only.** `back` shows a back control in place of the crumbs, named after the list it returns to. Use it for a target reached from one list, such as a chat opened from the session list.

Every crumb but the last is a link.
The last crumb is the page, in `text-1` with `aria-current="page"`.
A crumb that does not fit is cut, and it shows its full text on hover.
The path is where the item sits, not the list you came from.
An issue's path contains its project and leaves out the saved view.

## Selection and the path

The inspector shows the selection, and the path stays as it is while you select rows.
Opening an item goes to it and changes the path.
Give each row an open action, and give the inspector one too.

## Phones

On a phone the shared sidebar is a drawer, and the inspector is a sheet behind a button in the bar.
Each drill level is a screen of a `NavigationStack`.
The back control shows the title of the screen before, and the crumbs are not shown.
List screens have a large title.
A view built from `ViewLayout` and `ViewHeader` gets this with no extra code.
See [Phones](../phones.mdx#navigation).
